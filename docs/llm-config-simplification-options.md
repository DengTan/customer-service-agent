# LLM 配置简化方案 — 决策选项

## 背景
- 当前状态：配置了 Provider + 手动选模型
- 目标：用手动选的模型，忽略 Provider
- 约束：不需要向前兼容老用户

---

## 决策点 1：清理范围

### 选项 A：保留字段但废弃逻辑 ⚠️
- **操作**：数据库保留 `llm_provider_id` 字段，前后端不再读写
- **优点**：风险低，无需 migration，老数据保持原样
- **缺点**：代码中留下"半废弃"字段，容易混淆；settings 表仍有冗余列
- **工作量**：小（仅修改代码逻辑）

### 选项 B：彻底删除字段 ✅ 推荐
- **操作**：数据库 migration 删除 `llm_provider_id`，前后端同步清理
- **优点**：清理彻底，无遗留概念，代码路径清晰
- **缺点**：需要迁移脚本（但你明确不需要兼容老数据，风险可控）
- **工作量**：中（migration + 前后端清理）

---

## 决策点 2：Provider 管理界面

### 选项 A：保留 Provider CRUD 🔧
- **保留功能**：
  - 用户可添加/编辑/删除 Provider（管理 API Key）
  - 可测试连接、启用/禁用
- **移除功能**：
  - ❌ "设为当前/当前使用"按钮
  - ❌ `onProviderChange` 回调
- **适用场景**：多个 OpenAI/Anthropic 账号切换使用

### 选项 B：完全隐藏 Provider 管理 🚫
- **操作**：设置页移除 Provider 管理分区，仅保留模型选择器
- **后果**：API Key 配置需要改为环境变量或数据库直接操作
- **适用场景**：单租户部署，Provider 由运维配置

---

## 决策点 3：模型选择器行为

### 选项 A：必填项 ✅ 推荐
- **行为**：
  - 下拉框无"请选择模型"空选项
  - 保存时校验 `ai_model_id` 非空，否则提示错误
- **优点**：强制用户明确选择，无歧义
- **缺点**：首次配置多一步操作

### 选项 B：自动选第一个可用模型 🤖
- **行为**：初始化时自动填充列表第一项（如 `qwen2.5:7b`）
- **优点**：开箱即用，零配置
- **缺点**：用户可能不知道当前模型是什么（隐式行为）

---

## 决策点 4：模型未配置时的错误处理

### 选项 A：禁止发消息 🚨 推荐
- **行为**：
  - 后端检测到 `ai_model_id` 为空时返回 `400 Bad Request`
  - 前端弹窗提示"请先在设置中配置 AI 模型"
- **优点**：强制配置，防止误用默认模型
- **缺点**：用户体验略差（但明确）

### 选项 B：降级到系统默认模型 ⚠️
- **行为**：
  - 后端读取 `ai_model_id` 失败时，自动使用 `qwen2.5:7b`
  - 前端显示黄色提示条"当前使用默认模型，建议配置"
- **优点**：对话不中断
- **缺点**：用户可能不知道在用哪个模型，token 消耗/响应质量不可控

---

## 推荐组合方案 ⭐

```
决策点 1: 选项 B — 彻底删除 llm_provider_id
决策点 2: 选项 A — 保留 Provider CRUD（移除"设为当前"按钮）
决策点 3: 选项 A — 模型选择器必填
决策点 4: 选项 A — 未配置时禁止发消息
```

### 理由
- **清理彻底**：无遗留字段，代码路径单一
- **灵活性**：保留 Provider 管理，支持多账号切换
- **安全性**：强制配置模型，避免隐式默认值
