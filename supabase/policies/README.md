# RLS Policy-as-Code (RC-2 / Phase B / B1)

This directory is the **single source of truth** for Row-Level-Security policies.
Every application table MUST have a matching `.sql` file in this directory.

## Convention

| File pattern | Purpose |
|---|---|
| `<table_name>.sql` | Single-table explicit policy declarations |

The convention intentionally **collapses all roles to `service_role`** because:

1. The application layer (`src/lib/storage/database/supabase-client.ts`) uses the
   **service role** Supabase client for all DB access (stage A3).
2. `service_role` **bypasses RLS by default** in Supabase, so explicit policies
   for `service_role` are belt-and-suspenders, not a security boundary.
3. Removing the legacy `anon` / `authenticated` policies (stage A6) makes the
   PostgREST surface uniformly deny-by-default. All requests go through the
   `withApi` L2 gateway which verifies the JWT cookie and issues queries via
   the service-role client.

## When to add a new policy file

A new `.sql` file MUST be added whenever a new table appears in
`src/storage/database/shared/schema.ts`. The CI inventory test
(`tests/integration/policies/inventory.test.ts`) fails the build otherwise.

## File template

```sql
-- supabase/policies/<table_name>.sql
-- Phase B / B1: explicit service-role pin for <table_name>.
-- The application layer connects with service_role (bypasses RLS);
-- these policies are explicit so the snapshot tooling has something
-- to diff against. Tighten to a USING predicate if you ever expose
-- this table to anon/authenticated roles.

DROP POLICY IF EXISTS "<table_name>_service_role_all" ON public.<table_name>;
CREATE POLICY "<table_name>_service_role_all"
  ON public.<table_name>
  FOR ALL
  TO service_role
  USING (true)
  WITH CHECK (true);
```

## CI enforcement

| Workflow step | Command |
|---|---|
| PR — inventory + snapshot diff | `pnpm policies:inventory` + `pnpm policies:snapshot:check` |
| Write/regenerate policy files + snapshot | `pnpm policies:snapshot:write` |

The policy files are generated by `scripts/policies/generate-policies.js` (which also regenerates the snapshot). For local development, run `pnpm policies:snapshot:write` whenever schema.ts adds/removes a table.
